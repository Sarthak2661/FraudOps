# FraudOps Data Card

## Dataset Overview

FraudOps uses generated synthetic banking data to demonstrate fraud operations workflows without using real customer records. The dataset models customers, accounts, cards, devices, merchants, transactions, fraud labels, rules, alerts, cases, model metadata, and data-quality checks.

## Purpose

The dataset is designed for:

- Local fraud analytics and scoring demonstrations.
- Batch ingestion and quality-control testing.
- Point-in-time-safe feature engineering.
- Baseline model training and threshold experimentation.
- Analyst-console and Power BI reporting walkthroughs.

## Simulated Fraud Scenarios

- Behavior deviation
- Card testing
- Impossible travel
- Merchant fraud burst
- New-device takeover
- Transaction velocity
- Normal travel false positive

The normal-travel false-positive scenario is intentionally included so the pipeline must distinguish suspicious-looking legitimate behavior from confirmed fraud.

## Data Layers

- Raw: Parquet batches under `data/raw/`
- Validated: accepted records under `data/validated/`
- Rejected: invalid records and rejection reasons under `data/rejected/`
- Curated/features: analytical features and pipeline summaries under `data/curated/`
- Reporting: PostgreSQL views under the `fraudops_reporting` schema

## Labeling

Fraud labels are synthetic and include delayed-label fields such as:

- `fraud_label`
- `label_source`
- `label_available_at`
- `chargeback_date`
- `analyst_confirmed_at`

This approximates fraud operations where the final label can arrive after the transaction date.

## Quality Controls

The pipeline validates:

- Required fields
- Type compatibility
- Unique transaction IDs
- Positive amounts
- Valid timestamps
- Valid currencies
- Allowed channels and statuses
- Referential checks against customers, cards, devices, and merchants

Rejected records are quarantined rather than silently deleted.

## Known Limitations

- Synthetic data is useful for demonstrating architecture and workflow, but it is not a substitute for production data validation.
- Entity behavior is generated from scenario logic and seeded randomness.
- Population diversity, fraud typologies, customer demographics, and adversarial behavior are simplified.
- Power BI reporting includes seeded management rows when operational alert/case tables are empty.
