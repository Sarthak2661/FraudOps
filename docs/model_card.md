# FraudOps Model Card

## Model Overview

FraudOps trains baseline fraud-risk models for synthetic banking transactions and uses the selected model as one input to a rules and cost-sensitive decision engine. The current selected model is `hist_gradient_boosting`.

## Intended Use

- Rank synthetic banking transactions by fraud risk for a local analyst-console demonstration.
- Compare model, rule, threshold, and financial-cost behavior in a portfolio-scale fraud operations workflow.
- Support learning and discussion around chronological splits, point-in-time-safe features, and experiment tracking.

## Not Intended For

- Production fraud decisions.
- Real customer risk scoring.
- Automated account closure, legal action, or adverse customer decisions.
- Use on real personally identifiable information or payment data.

## Training Data

- Source: generated synthetic banking data only.
- Records used in current training artifact: 1,314 training rows, 438 validation rows, and 439 final-test rows.
- Training fraud rate: 2.21%.
- Split method: chronological split. The final test set is held out until model selection is complete.
- Feature version: `phase4_features_v1`.

## Features

The model uses point-in-time-safe transaction, customer behavior, device, and merchant features. Examples include:

- `transaction_amount`
- `is_new_device`
- `amount_to_customer_avg_ratio`
- `transactions_last_10m`
- `unique_countries_last_7d`
- `device_fraud_rate_history`
- `merchant_fraud_rate_30d`

Full definitions are in `docs/feature_dictionary.md`.

## Selection Rationale

`hist_gradient_boosting` was selected because it had the lowest validation expected financial cost while preserving PR-AUC and recall-at-capacity visibility. The final test set remained held out until after model selection.

## Risks And Limitations

- The dataset is synthetic and cannot represent the full complexity of real banking behavior.
- Reported metrics are useful for project validation, not production performance claims.
- Labels are generated by scenario logic and delayed-label simulation, not customer disputes or real chargebacks.
- The model can still create false positives and false negatives; decisions should remain explainable and reviewable.
- Model artifacts are excluded from Git. Recreate them with `python scripts\train_baseline_models.py`.

## Monitoring Recommendations

Before any production-like use, add:

- Data drift monitoring for amount, channel, country, merchant category, new-device rate, and velocity.
- Prediction drift monitoring for risk-score distribution, review rate, hold rate, and alert volume.
- Label-backed performance monitoring once delayed labels become available.
- Manual approval before promoting a challenger model.
